## Outcome

The current facade is not native daemon parity. Cargo workspace contains only `hrc-domain` and `hrc-kernel`; `HrcApi::post_owner` calls Bun's declaration resolve, runtime start and session restart APIs (`crates/hrc-domain/src/api.rs:111`, `summon.rs:65`, `restart.rs:37`). The kernel owns derived cardo presentation and wire operation handling, not authoritative runtime/store/placement/restart execution. `contract/` and `conformance/` directories do not yet exist in the inspected checkout.

Stage 2 needs a consumer-and-writer inventory in addition to its route table. Route conformance alone cannot prove the CLI, maintenance, auxiliary listeners, startup recovery or rollback. The strongest overlooked example is `hrc run annotate`: a direct SQLite writer bypassing either HTTP daemon's route owner. Keeping Bun source present and passing a facade test is insufficient to establish that Bun remains independently usable after Rust writes state.

## Other consumers and boundary cautions

ACP's old “twelve direct reads” is not a current exhaustive inventory. Source examples remain in ACP `packages/acp-server/src/real-launcher.ts` (launch IDs, run status, assistant completion and live session/runtime evidence), `integration/interface-run-dispatcher.ts:698` (activity), and `packages/acp-cli/src/hrc-store-reader.ts` (default HRC store discovery and diagnostic reads). Inventory call sites and SQL columns, not a historical count. Coordinate any ACP API migration with ACP; do not import its behavior into HRC tests or implement it here.

Conversely, an `hrc-store-sqlite` import in ACP does not prove a live HRC-store writer. ACP `packages/hrc-injector-core/src/injector-state-store.ts:42` opens the injector's own writable store; `hrc-mail-injector/src/policy/kicker-state-store.ts` likewise describes private state imported once from former HRC tables. Preserve exported repository/package compatibility until ACP advances its own producer tuple; distinguish private-store schema dependencies and one-time imports from ongoing state.sqlite reads. The injector remains ACP-owned. ASP declaration/preparation and broker wire protocols remain external contracts; keeping brokers separate is compatible with native daemon ownership and does not mean all Bun processes disappear.

## Required proof that Bun still works unchanged

“Unchanged” should mean preserved supported behavior, entry points, configuration and independent fallback. It cannot mean zero TS edits throughout stage 2: approved dual implementation and job ownership require coordinated changes. Freeze a baseline Bun release/config/dependency tuple and explicitly state which same-release Bun is the rollback target for each schema epoch. Test previous selected release too if backward rollback across releases is promised.

1. **Bun alone, kernel absent.** Existing just verify TS leg and installed smoke remain green with no Rust process or front dependency. Start a real blank agent in scratch through installed Bun, send a second turn, observe final turn.message and turn.completed, inspect/attach in real PTY, resume/restart seat and terminate. Verify errors, JSON/NDJSON, exits and selector identity. Facade success is not evidence of this independence.
2. **Bun plus kernel.** Repeat meaningful operations, ensure derived state follows, stop/restart kernel and show Bun continues serving; prove pinned read set remains side-effect-free with a mutating-read control. Summon/restart current fixture tests in `crates/hrc-kernel/e2e/{summon,restart}_e2e.py` use Python fake owner servers; these prove wire mapping/failure behavior, not native ownership or real Bun lifecycle. Preserve separate real installed gates.
3. **Split mode with actual ownership.** Use the same unchanged CLI and SDK over the front AND direct Bun private socket, all direct-store consumers above, real broker and ASP preparation. Exercise Bun and Rust writes and both directions of subscriptions. Kill or pause Bun: a supposedly native slice must still work, while a proxy slice must fail honestly. That negative control distinguishes native parity from accidental delegation.
4. **Rollback using shared history.** After Rust creates sessions/runtimes/events, annotations, operations and retry state, stop/fence Rust owners in scratch, transfer endpoints and all jobs to Bun, then continue the same real broker/session. Preserve generation, ledger incarnation/high-water, submission idempotency, stream cursors, permissions and credentials. Read/export/verify Rust-created evidence through Bun tools. Reversing a public socket alone does not transfer job ownership, private socket discovery or broker connections.
5. **Install/restart/fleet.** Commit/install activation and publish remain separate. Operator (Mable authorized seat) activates releases. Capture status required keys with existence/type assertions: `.release.runningEqualsInstalled`, sourceCommit and binaryPath/packagePath at actual observed locations, selected/running tuple. Diff per-runtime warmup failure identities and prove active turn completion after reattach. Test mixed Bun/Rust federation peers both directions, host authority/claims, refusal and retry/replay, remote monitor routing and streamed disconnect. Perform pilot→svc→max3 only through an explicitly supported deployment procedure.
6. **State/scale.** Use SQLite backup or VACUUM INTO for coherent snapshots, never cp of a live WAL database. Include holes, retained maximum deletion, large/spilled payloads, malformed stored JSON, FTS, busy writer and crash/reopen. Preserve hrcSeq versus streamSeq distinction and imported origin identities. Demonstrate bounded memory and stream latency on representative data; functional equality on empty fixtures is insufficient.

Every scenario needs command, release/config identity, asserted expected result, control case and durable logs under task artifact_dir. Normalize generated IDs/timestamps only for comparisons; do not erase missing fields, event ordering, errors or side effects. Baseline known failures must be documented rather than called regressions or silently accepted. No such runtime validation was performed by this audit.

## Recommended dependency order

1. Reconcile delivered stage 1/1b status; freeze full executable route/alias + direct consumer + store/file/listener/job inventory. Update EVERY active architecture record stating the moved boundary; obtain Daedalus review before implementation.
2. Establish Bun-only installed baseline and externally runnable neutral conformance harness, real-server-sampled schemas and controls. Include direct store and release compatibility, not just requests.
3. Define public/private endpoint discovery, process locks and supervision, one migration owner, native writer transaction rules and both directions of cross-process notification. Specify transfer/fencing/recovery of startup and recurring jobs. These are prerequisites, not details to defer until a later slice fails.
4. Port only proven side-effect-free reads first; keep liveness-reconciling reads with their mutation owner. Complete direct-store and auxiliary ingest contracts before porting any write owner. Resolve external wrkq/ASP contracts ahead of affected lifecycle/message work.
5. Port cohesive state owners under the state audit's revised order. Each lands only after Bun-alone, native-discriminator, mixed mode and real rollback proofs pass; then supported installed pilot and fleet soak.
6. Retire Bun daemon only after ALL native authority, background work, recovery and operational consumers pass. “No HRC Bun tooling” is a separate deliverable: Bun CLI/SDK/direct-store utilities, build/publish/install scripts and ASP broker dependencies remain unless separately replaced. Do not remove repository packages merely because Rust owns HTTP routes.

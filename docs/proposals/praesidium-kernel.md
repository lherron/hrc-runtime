## 0. Claim

The taxonomy record unifies what is *read*: one cardo document, `praesidium`, projecting nine subjects from three systems under one vocabulary. It was written for one reader, Loggia, and hosted inside rusthrc on that assumption. With every agent as a consumer, two things change:

1. **The host moves out of rusthrc.** The surface every agent's tools run through must not share a process with the daemon that births, rotates and restarts those agents. It becomes its own kernel, the idiomatic cardo shape (foundry-kernel, raspd's aspd kernel, rusthrc's hrc kernel, cardo-proof each host their own), one per node, reading HRC the way the record already reads peers.
2. **The record gains the half agents use.** A document answers "what is the current situation"; an agent also writes, reads history and bodies, waits, and must be *who it is* in every ledger row. That is an operation catalog with caller identity, served as one CLI, `prae`, whose subcommand tree is generated from the declarations. cardo already has the mechanism: discovery lists every operation with its schema, and `cardo-agent` serves durable write outcomes on an `agent.sock` beside `kernel.sock`, as foundry-kernel does today.

The owners stay as they are. wrkq, HRC and agent-spaces keep their stores, APIs, fences and authority. Agents stop calling them. An old register moves only by a per-subject ruling that deletes the old path in the same campaign. The kernel holds no store of its own in revision one (r1.1, F3): a register about a shared subject lives with the system that mints the subject, because every node's consumers reach that system and would not reach a node-local store.

## 2. Shape

### 2.1 Process

One **praesidium kernel** per node: a Rust binary in its own repo and wrkq project, **`praesidium-kernel`** (RULED), never a crate inside hrc-runtime, a cardo host on `var/run/praesidium/kernel.sock` with a `cardo-agent` host on `var/run/praesidium/agent.sock`, state under `var/state/praesidium/` (the `praesidium.cardo` snapshot, a cache and never authority), `com.praesidium.praesidium-kernel` under launchd, in `just fleet-status` from day one. ### 2.4 The operation catalog: the standard

Operations are the standard agents migrate to; the document is the cache in front of them. Three tiers, every one declared with `effect`, `fences`, caller arguments and, for writes, `idempotency`:

1. **Read the situation**: cardo queries over the `praesidium` document by type and key (`seat.list`, `task.list`, `room.get` with its `members` field, `feed.list`). Answered from the snapshot; every result carries the `feed` state so an agent can see it is reading stale.
2. **Read history and bodies**: `effect: read` operations delegated to the owner, because record R3 and §6 keep ledgers, closed tasks, terminal envelopes and bodies out of the document and that stays true. wrkq: `task.get`, `task.find`, `task.history`, `task.comment.list`, `room.history`, `room.mail.get`, `room.mail.find` (the inbox: pending and presented mail to the caller, bodies included), `seat.handoff.get`, `promise.get`, `promise.find`, `work.group.history`, `task.workflow.get`. HRC: `seat.get`, `seat.history` (turns, runs, events), `generation.get`, `runtime.get`, `runtime.list`, `node.get` (server status). Sweeps that the owner runs on a read (`envelope.pendingView`, `inboxView` behind `room.mail.find`) run as they do today, under the caller's identity, because the caller is the addressee.
3. **Write**: `effect: write` operations delegated to the owner through `agent.sock` (durable admission, receipt, idempotency key = the tool call's `action_id`, as foundry). wrkq: `task.create`, `task.update`, `task.move`, `task.archive`, `task.remove`, `task.claim`, `task.release`, `task.comment.create`, `work.group.create/update`, `room.say`, `room.join/leave`, `room.mail.defer/withdraw`, `promise.create/renew/resolve/abandon`, `task.workflow.attach`, `project.event.create`, `task.attachment.create`, `workstream.create/update`, `ext.put/delete` (subject task, work group, room; M5). HRC: `seat.summon`, `seat.send`, `seat.interrupt`, `seat.restart` (the rotation door; carries M1's handoff), `seat.update` (session metadata), `seat.asks.create/update`, `seat.handoff.create/acknowledge`, `ext.put/act/delete` (subject seat; today's annotations, same shape as M5 by D8). Waits (`wrkq monitor wait`, `hrc monitor`) are read operations with a bounded timeout over the owner's wait primitive (`monitor.stateView` polling; `events/bounded-stream`), not kernel-side loops.

**Reconciliation class (r1.1, F2; r1.2 narrowed after the second cycle).** **The kernel never repeats a write on its own.** Its `agent.sock` journal records admission and outcome; an outcome the owner answered but the kernel could not journal is reported to the agent as `uncertain {operation, action_id}` for every class, exactly as a lost CLI reply is today, and the agent decides. What a class declares is what the *agent* may safely do next, under the owner's own contract, and it is published by `prae describe` and in the parity table, taken from the owner's declaration at build time and never assumed:

- **`keyed`**: the owner replays by idempotency key. The kernel passes the tool call's `action_id` as the owner's `idempotencyKey` on the first call; the agent may repeat with the same `action_id`, and the owner returns the recorded result or `idempotency key reused with a different request`. wrkq: `task.create`, `task.update`, `task.comment.create`, `room.say`, `project.event.create`, `work.group.update`, `task.relation.create`, `task.workflow.attach`, `task.attachment.create` (wrkq's `handoff.create` is keyed too but retires with M1). HRC: `seat.summon` (claim-and-start replays by key). **The replay guarantee is the owner's, including its window:** wrkq records the replay row in a separate insert after the effect commits (`wrkqapi/comments.go:43–93`, `api.go:135–147`), so a wrkqd interruption inside that window leaves an effect whose key the owner never recorded. That window is the same for the CLI today, is the owner's to close (cardo's wire v2 idempotency rule puts deduplication in the product transaction), and is explicitly unsupported here (§6); the kernel neither claims to cover it nor gates it.
- **`fenced`**: the owner takes an etag or revision fence on the first call. The agent repeats with the same fence; success means the write landed once, `conflict` means something landed and the current state is read to tell which. wrkq: `task.move`, `work.group.archive/move/remove/update`, `task.comment.remove`, `task.restore`. HRC: `ext.put`, `ext.delete` on a seat (today's annotation put/delete; both take `expect`, `projection/sessions.rs:443–467`), `seat.asks.*`, `seat.handoff.acknowledge`.
- **`unkeyed`**: the owner records neither, or ignores what is sent. The agent reads before deciding. HRC: `seat.send` (literal input stores the key but does not replay it, and delivers before recording), **`ext.act` on a seat** (today's annotation act: the route calls `act_annotation` without `expect` and the store appends an action event without changing the annotation, `hrc-store/src/annotations.rs:436–466`; a repeat appends a second action), `seat.interrupt`, `seat.update` (session metadata, unfenced by contract), `seat.restart`. wrkq: `room.mail.defer/withdraw`, `promise.*`, `task.claim/release`, `room.join/leave`.

An `unkeyed` operation that agents use heavily is a candidate for an owner additive before its verbs migrate: HRC enforcing the `idempotencyKey` its literal-input table already stores (a keyed lookup in `active_input_deliveries` before delivery) would move `seat.send` to `keyed`. Named here as the one such additive worth proposing; until it lands `seat.send` is `unkeyed` and `prae describe seat` says so.

**Naming (r1.3).** An operation is `type.verb`, where the type is the taxonomy's `subject[.kind]` (record R2) and the verb comes from **one grammar derived from the registers**, never from an owner's CLI or RPC spelling. wrkq's `cat`, `ls`, `touch`, `set`, `mv`, `rm`, `tree` and `log` are Unix file metaphors that stop at its CLI; its RPC names (`task.catView`, `task.findListView`, `envelope.inboxView`) are view names that stop at its wire. The parity table maps each of them to a grammar verb; the mapping is the table's job, not the name's.

| register | verbs | meaning |
|---|---|---|
| any | `get` · `list` · `find` | `get {key}` reads one record from its **owner**, bodies and fence included (today's `cat` / `show`); `list {filter}` reads many from the **document**, current situation only; `find {query, state}` searches the owner, closed and terminal included |
| identity | `create` · `archive` · `remove` · `move` | mint; retire; soft-delete; re-parent |
| state | `update {expectEtag}` | one fenced write of the fields named; no separate `set`, `patch` or `edit` |
| obligation | `say` · `reply` · `defer` · `withdraw` · `acknowledge` · `resolve` · `abandon` · `renew` · `wait` | open, answer, pause, cancel, consume, satisfy, drop, extend, and block until a state with a bounded timeout |
| ledger | `history` · `create` on the ledger type | `history {key, kinds, since}` reads a subject's ledger (comments, transitions, events, room log, turns, runs); appending is `create` on the ledger type (`task.comment.create`) |
| extension | `put` · `get` · `list` · `delete` · `act` | one shape for HRC's seat annotations and wrkq's M5 extensions (D8): `ext.put {subject, ns, kind, id, body, expectEtag}` |

Subject-specific verbs are the closed set the grammar cannot express: `seat.summon`, `seat.send`, `seat.interrupt`, `seat.restart`, `task.claim`, `task.release`, `room.join`, `room.leave`, `task.workflow.attach`. Nothing else may add a verb without amending this table.

**Gap rulings (r1.7, mable under Lance's delegation, 2026-11-02; parity table T-12246 P1–P6).** No new verb. Each gap is an existing verb with an argument or a field, and the parity table maps to it:
- P1 `wrkc members` → `room.get` (members are a field of the room's identity record; no `room.members` and no `room.member` type).
- P2 `hrc peek`, `hrc runtime capture` → `runtime.get --screen` (a bounded capture of the current pane returned as a field of the owner read; transient, never projected).
- P3 `hrc start` → `seat.summon` (its declared arguments carry prompt, provisioning and placement; `hrc start`'s flags map onto them in the table).
- P4 `hrc resume` → `seat.summon --continuation resume` (resume the existing continuity on its prior host; refuses `no_continuation` rather than silently summoning fresh; `--continuation fresh` is today's summon).
- P5 `hrc turn` → `seat.send` then `seat.wait` (`wait` is the obligation-register verb with a bounded timeout over `events/bounded-stream`; output is read through `seat.history`). Tracked dispatch is the pair, not a verb.
- P6 `hrc runtime terminate` → `runtime.archive --continuation keep|drop` (identity-register retire; distinct from `seat.interrupt` and `seat.restart`). There are no aliases: the inbox is `prae room mail find --to me` and its help text says "your inbox"; `wrkq monitor wait` is `prae task wait`; `hrc restartme` is `prae seat restart`. The **parity table** (every one of the 168 CLI forms → `type.verb`, or → "human only", or → "retired", each write with its reconciliation class) is an artifact of step 1 (§9) and the subject of gate 1; the catalog is complete when the table has no blank row.

**Not an operation.** `hrc server restart/stop`, `just install`, `hrc daemon` lifecycle, `wrkq index`, webhooks, `wrkf.*`: operator and workflow-engine surfaces, human or wrkf only. Restart authority stays exactly where the restart doctrine puts it. (Restored in r1.3; dropped by an editing mistake in r1.2.)

### 2.5 Caller identity

Every operation carries the caller: `{principalRef, scopeRef}`.

- **Bound per invocation.** `prae` (§2.6) runs inside the runtime's environment and reads what `wrkq` and `hrc` read today: the principal, `HRC_SESSION_REF`, `HRC_RUNTIME_ID`, and the daemon-minted lifecycle credential at `<runtimeRoot>/lifecycle/<runtimeId>.credential` (r1.1, F1). It presents all of them in its hello on `agent.sock` for a write and the principal and scope as a query attribute on `kernel.sock` for a read, on every invocation. The kernel **refuses a hello whose scope is not a live seat in its `hrc@<this node>` binding** (`unknown_caller`), and refuses a principal that is not that seat's agent. The kernel never verifies the credential itself; HRC does.
- **Forwarded, never substituted.** To wrkqd as `X-Wrkq-Principal-Ref` plus the scope params the method takes, so every ledger row names the agent, not the kernel (gate 2). To HRC as the three lifecycle headers (`x-hrc-lifecycle-session-ref`, `-runtime-id`, `-credential`) on every HRC operation, verbatim, so `credentials::verify_caller` sees the runtime that is calling, binds it to its live scope and generation, and `seat.restart` and the lifecycle route refuse or admit exactly as they do for `hrc restartme` today. **HRC changes nothing for identity**; the r1 "caller scope on operator routes" additive is withdrawn. Trust level: wrkq operations are self-asserted as today plus the seat-table check; HRC lifecycle operations carry the daemon-minted credential as today. Neither is a new authority model.
- **`cause`.** Every command carries `{principalRef, scopeRef, taskId?, action_id}` as its cardo `cause` (wire v2 §12), so receipts and the kernel's own ledger say who and why.

### 2.6 Transport: the `prae` CLI, shaped like wrkq (RULED)

- **One binary, `prae`**, shipped by the kernel repo, is the agent surface. **Its callers in revision one are processes inside an HRC runtime's environment** (r1.5, F4): the agent's harness and the hooks that run in that environment, such as the turn-end asks backstop. A process without `HRC_SESSION_REF`, `HRC_RUNTIME_ID` and a live seat is refused `unknown_caller`, and that is the admission predicate, not a gap in it. Its subcommand tree is `prae <type> <verb> [key] [flags]` over the grammar of §2.4, **generated from the kernel's declarations at build** (types, verbs, fields, fences, classes), so adding a type to the kernel adds its commands. Conventions are wrkq's: `--json` and `--ndjson` for structure, `--one`; bodies as `-m '<text>'`, `- <<'TEXT'` (quoted heredoc) or `@file`; `--if-match <etag>` for the fence; `--to`, `--fyi`, `--note`, `--discharges` on `room say`; `--state`, `--limit`, `--cursor` on `list` and `find`; a timeout on every `wait`. Reads go to `kernel.sock`, writes to `agent.sock`, identity per §2.5.
- **Results.** Without `--json`, one line per record as wrkq prints today. With `--json`, `{result, class?, action_id?, feed}`. Refusals exit non-zero with the code on stderr (`unknown_caller`, `owner_unreachable`, `foreign_seat`, `conflict`). **An uncertain outcome exits 7**, distinct from every refusal, with `uncertain: <type.verb> <action_id>` on stderr and, for a `keyed` type, the offer `repeat with --action-id <id>`; `--action-id` on a write repeats under the owner's replay (§2.4). Scripts can therefore tell "did not happen" from "do not know".
- **`prae describe <type>`** prints the type's owner, register, key form, fence, class, fields, verbs, ledger types and projection window from the declarations. It replaces the injected `wrkq info` / `wrkc info` guides for agents in the space (S1), never for anyone else; `prae --help` and `prae <type> --help` are generated from the same source.
- **Provisioned as a space.** A `prae-tools` space (placeholder name, §7) in `spaces-repo` puts `prae` on the harness PATH and nothing else; raspd composes it into every harness home. An agent whose spaces exclude the space keeps the old CLIs; that is the migration unit (S1, gate 5). The turn-end asks backstop, a harness hook that runs inside the runtime's environment, uses the same binary and binding. **Daemons are not callers** (r1.5, F4, F5): the mail injector, ACP, taskboard and the kicker keep their own direct wrkq and HRC clients and their own service identities (the injector writes as `agent:hrc`, `agent-control-plane/packages/hrc-mail-injector/src/wrkq-ledger.ts:13,40–66`, and is the sole external mail delivery owner, `index.ts:55–58`), so addressed-mail delivery to any seat, migrated or not, never depends on a kernel (gate 3, S1, S4). lefthook and other shell checks do not call `prae`. Humans outside a runtime keep `wrkq`, `wrkc` and `hrc` (K8); an operator caller is §7.
- **Agents are not migrated in place (RULED, Lance 2026-11-01).** The migration unit is a **new agent**: a profile under `var/agents` whose prompt and skills reference `prae` only, with every `wrkq`, `wrkc`, `hrc` and `asp` form stripped, and `prae-tools` in its spaces. Existing agents and their prompts are untouched; an existing agent retires only when its `prae` successor has carried its load, under S2's same-campaign rule. **Every agent gate in this campaign (1, 2, 2a, 5) runs on the new agents**, never on a legacy agent with the space added. The cohort starts small (§7.5) and grows role by role.
- **No hard cutover (RULED, Lance 2026-11-01).** aspd, HRC and wrkq stay functional for every caller throughout: owner changes are additive (D12 read views and incarnation; seat kind, work, asks, handoff), migration is per agent by space, the old CLIs stay for humans, daemons and unmigrated agents, and the `hrc` document stays open until Loggia has moved. The only retirements are of a single surface after its replacement is gated: the `wrkq handoff` shim after M1's import and hand assignment, the `hrc` document after gate 1, and the M4/M5 writers under their own specs.
- **No MCP bridge in revision one.** If one is wanted later it is generated from the same declarations, shaped one tool per verb with the type as an argument, and is its own record. Loggia and tests keep the raw socket.

### 2.7 Degradation and persistence

Unchanged from the record §3.8–3.9 and D17: persisted snapshot, resume at last-good, stale-never-absent, `feed` node per binding, `praesidium kernel rebuild` discards the cache. Two additions for agents: a **read tool answers from a stale snapshot and says so** (the result carries the subject's `feed` state and `cursorAt`), and a **write tool to an unreachable owner refuses `owner_unreachable {owner, since}`** rather than queueing, because the owner's fence cannot be supplied from a snapshot and a queued write would be the kernel acting later with authority it does not hold (record §3.8 rule 3).

### 2.8 Multi-node

One kernel per node. Each binds every HRC node's page, so an agent on svc sees max3's seats, with `node` on each. Each node's wrkq binding reads the one canonical wrkqd on mini, so every node sees the same tasks, rooms and extensions (r1.1, F3: nothing shared is node-local). Agents use their node's kernel. The `hrc@<node>` binding for the local node goes over the same HTTP routes as the remote ones, on loopback.

## 3. Rules: the strangler contract

- **S1 Surfaces are replaced.** Every CLI form an agent uses gets an operation, a parity-table row, and a `prae` command. Migration is by new agent (§2.6), one role at a time; existing agents are never edited onto `prae`. The injected `wrkq info` / `wrkc info` guides are suppressed only for agents in the `prae` space (the space carries the suppression) and stay injected for everyone else until the last agent has moved; `prae describe` replaces them per agent, never fleet-wide. **Clarified r1.8 (2026-11-02, T-12312):** HRC injects no guides; the `wrkq info` / `wrkc info` text reaches a seat only through exec reminders in the agent's own `context-template.toml`. Because the migration unit is the whole new agent, the cohort's template simply omits them and injects `prae describe …` instead; that template is the suppression. No env, marker or HRC switch exists or is needed, and no legacy file changes (gate 5 byte-identity). Fully committed.
- **S2 Stores move one subject at a time, by ruling.** A subject's identity, state, obligation or ledger register leaves its owner only when the kernel reproduces its full lifecycle (fences, sweeps, obligation discharge, federation routing), gates it, and **deletes the old path in the same campaign**. No deferred retirement. Merging daemons or stores wholesale remains unsupported (record §6, D1).
- **S3 Projection tax.** Once a register is read through the kernel, an owner change that the kernel does not project is incomplete. Each owner's definition of done gains "projected in the praesidium kernel or declared human-only".
- **S4 Dependency direction.** HRC, wrkq and aspd never call the kernel, and neither does any fleet daemon on the delivery path: the mail injector, the kicker, ACP and taskboard keep their direct clients. Handoff stays in HRC (rotation injects it; record M1). The kernel is a client of the owners and a dependency of nothing that delivers to an unmigrated seat.
- **S5 A new register lives where every one of its consumers can reach it.** In revision one that is the system that mints its subject (record R1), because the kernel has no shared store and a node-local one would partition writers from consumers on other nodes (F3). The kernel becomes a candidate home for new registers only under a shared-store design of its own (§6), which this record does not propose. The r1 claim that owners stop growing from phase 4 is withdrawn.

## 5. Decisions

| id | decision | why |
|---|---|---|
| K1 | A separate kernel process per node, not a document inside rusthrc. | The surface every agent runs through must not share a failure domain, restart authority or release cadence with the daemon that births and rotates agents; it is the idiomatic cardo shape; it inherits none of rusthrc's eight single-document assumptions; max3 stops being special. |
| K2 | The operation catalog is the standard; the document is a cache in front of it. | Agents write, read history and bodies, and wait. R3 keeps those out of the document and that is right; delegated read-through ops serve them under the owner's own sweeps. |
| K3 | Caller identity is bound per connection from HRC's environment, including the daemon-minted lifecycle credential, checked against the live seat table, and forwarded verbatim to every owner; HRC verifies the credential as it does for the CLI. | Parity with today's trust plus one check the CLIs never make; every ledger row keeps naming the agent; `seat.restart` and the lifecycle route keep their credential admission with no HRC change (F1). |
| K4 | The agent surface is one CLI, `prae`, shaped like wrkq and generated from the declarations; agent-spaces provisions it as a space; no MCP bridge in revision one. | Lance's ruling; every harness and in-runtime hook already drives a CLI; one binary serves the runtime's processes with one identity binding (humans and daemons are not callers in revision one, §2.6); space membership is a per-agent migration switch with trivial rollback. |
| K5 | Writes go through `agent.sock` with durable admission and outcome journaling; reads through `kernel.sock`. **The kernel never repeats a write.** An uncertain outcome is reported as uncertain for every class; the class tells the agent what a same-key or same-fence repeat means under the owner's own contract. | The kernel cannot close an owner's transaction boundary (wrkq's post-commit replay insert; HRC's fenceless action append), so it claims nothing about duplicates beyond what the owner records (F2, two cycles). An uncertain outcome is what the CLI gives today. |
| K6 | A write to an unreachable owner refuses; it is never queued. | The kernel holds no authority of its own; a queued write would execute later with a fence the caller never supplied. |
| K7 | Old registers move by per-subject ruling with same-campaign deletion; new registers live where every consumer reaches them, which in revision one is the minting owner. | No strangler graveyard: nothing is "retired later". No node-local store for shared subjects (F3). |
| K8 | Humans keep the CLIs in this record. | The goal is the agent surface; a human CLI over the kernel is a separate decision with its own ergonomics. |
| K9 | The persisted document, stale-never-absent, and the `feed` node are adopted unchanged. | With agents as consumers they are essential, not optional: an agent on max3 must keep reading when mini's wrkqd blips. |

## 6. Explicitly unsupported

Merging daemons or stores; the kernel holding write authority, fences or a store of its own; the kernel verifying or minting lifecycle credentials (HRC does); queuing writes for an unreachable owner; the kernel repeating any write on any outcome; closing an owner's own replay window from the kernel (wrkq's replay row is inserted after the effect commits; a wrkqd interruption inside that window is the owner's defect, reachable from the CLI today, and not gated here); the kernel as a dependency of HRC, wrkq or aspd; replacing `wrkf.*`, webhooks, index or daemon-lifecycle surfaces; an MCP bridge in revision one; aliases of any kind (the inbox is `prae room mail find --to me`); renaming room; any daemon as a `prae` caller (mail injector, kicker, ACP, taskboard); `prae` in lefthook or any shell check outside a runtime; a human or service caller without a live seat in revision one; a node-local register for any shared subject; inferring the caller from anything but the provisioned environment; projecting ledgers, closed tasks, terminal envelopes or bodies into the document (they are read-through ops); hierarchies while the `hrc` document is live; seat records (`asks`, `work`, `kind`, `handoff`) anywhere but HRC; remote send, summon or rotation beyond what the home already allows.

## 8. Acceptance, if built (product claims; readback from ledgers, stores, transcripts)

1. **Tool parity.** A task-scoped clod with `prae-tools` in its spaces and **no `wrkq`, `wrkc` or `hrc` on its PATH** takes a real wrkq task through claim, progress comments, a mail exchange with another seat, a handoff and completion, using `prae` only. The parity table has no blank row for the verbs it used. Transcript and ledger rows are the evidence.
2. **Identity survives the hop.** Every row that run wrote (`tasks.*_scope_ref`, `event_log.scope_ref`, envelope `from_scope_ref`, `hrc_events`) names the clod's principal and scope, never the kernel's. A hello with a scope that is not a live seat is refused `unknown_caller`. `prae seat restart` rotates the clod's runtime and the handoff lands in generation N+1; the same call with the credential header stripped is refused `credential_missing` by HRC, not by the kernel.
2a. **Uncertain outcomes are reported, never repeated.** Kill the kernel after the owner answered and before the journal wrote, once for a `keyed` operation (`task.create`) and once for an `unkeyed` one (`seat.send`): both commands exit 7 with `uncertain: <type.verb> <action_id>`, the kernel's journal shows no kernel-initiated repeat, and the ledger holds one row for each. Then the agent repeats `task.create` with the same `action_id`: wrkq returns the recorded result and the ledger still holds one row. `prae describe ext` says a repeat of `act` on a seat appends a second action.
3. **Isolation both ways.** Kill the kernel: HRC, wrkqd and every agent still on the CLIs are unaffected; agents on `prae` get a non-zero exit, not a hung turn. Restart rusthrc: `prae` reads keep answering from the snapshot with `feed{hrc@max3}` stale; writes to HRC refuse `owner_unreachable` until it answers; wrkq writes keep landing.
4. **One model.** Loggia mounted on `praesidium:praesidium` and `prae seat get` from an agent return the same node for the same seat, including a seat homed on svc, with no second mount.
5. **Cohort isolation.** A new `prae` agent has no `wrkq`, `wrkc` or `hrc` on its PATH and its prompt and skills contain no reference to them (grep count zero, recorded); the legacy agent of the same role is byte-identical before and after the campaign step; the new agent completes gate 1's task. Nothing about a legacy agent changed, so nothing needs restoring.

## 10. Sizing, honestly

This is the largest re-platforming praesidium has attempted. Phases 1–4 are each a campaign of several task-scoped seats over days, not hours; phase 5 is a long tail across 154 files that runs while everything else proceeds. Two surfaces coexist for the whole of phase 5. The kernel becomes the critical path for every migrated agent write, where today only Loggia depends on cardo. Against that: one vocabulary and canonical keys everywhere; one CLI generated from the declarations instead of 1,226 hand-encoded references to three; agents and operator reading one model with the same degradation guarantees; owners that stop growing from phase 4 on.
